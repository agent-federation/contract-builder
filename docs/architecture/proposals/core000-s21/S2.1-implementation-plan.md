## 4. Proposed S2.1 scope

### 4.1 Goal

Extend the existing five-claim S1 slice to the accepted model surface without changing generic-core
behaviour:

- 8 → 14 entity kinds;
- 11 → 28 relation declarations;
- 13 → 24 policy-check codes (S2-D1 A);
- S1 structure excerpt → the full public structure (components, interfaces, phases, transitions,
  extension points, trust boundary, diagnostics, dependencies);
- `conformance_case` kind/schema and manifest pointer with `conformanceCases: []`;
- preserve the five S1 claims, their statuses and their relations;
- 19 → 28 profile-closure files, 10 → 16 schemas.

### 4.2 Explicit non-goals

- No `spec/lib/` change, no new core capability, no CLI/API implementation, no G4 closure.
- No 78-claim register, no claim promotion, no regression of the five S1 claims (S2.2).
- No focused failing tests for the 11 new checks (S2.3); no N1–N18 matrix (S3).
- No durable evidence, no committed CORE-000 draft (P-2/P-3/P-6 commit points belong to S2.2/S2.3
  after a successful full-model run; the transient harness record is still produced by tests).
- No H2/H3 result, no independent verification record, no sandbox/isolation claim.
- No change to the accepted design, execution plan, decision record or S2 package.
- No change to `CORE-001.legacy.md`, `spec/`, `profiles/core001/`, `pap/`, `package.json` or
  `bun.lock`.

## 5. Proposed model surface

### 5.1 Entity kinds (14)

Existing eight remain; six are added. Fields are from design §5.3; all schemas keep the reserved
names (`id`, `kind`, `type`, `provenance`, `verification`, `relations`, `review`).

| Kind | Required fields (proposed schema) | Optional | Reserved-name note |
|---|---|---|---|
| `phase` | `id`, `name`, `guarantee`, `not_guaranteed` | `public` | — |
| `transition` | `id`, `condition`, `description` | — | phase endpoints via `startsAt`/`endsAt` relations |
| `dependency` | `id`, `name`, `kind`, `status` | `version`, `consequence` | `kind` is reserved and stripped: the value is read from the source document (see §6.2) |
| `extension_point` | `id`, `name`, `mechanism`, `trust`, `status` | `description` | — |
| `diagnostic` | `id`, `code`, `severity`, `phase`, `message`, `status` | `disposition`, `blocking` | — |
| `conformance_case` | `id`, `kind`, `input`, `expected`, `status` | `notes` | `kind` is reserved and stripped (see §6.2) |

ID patterns proposed for review: `^PH-[A-Z0-9-]+$`, `^TR-[A-Z0-9-]+$`,
`^[a-z@][a-z0-9@._/-]*$` (dependency = manifest name), `^EXT-[A-Z0-9-]+$`,
`^(core000|core)\.[a-z0-9.-]+$` (diagnostic id = catalog code), `^CC-[A-Z0-9-]+$`.

`claim.schema.json` already declares `subject_kind` over
`component|interface|phase|transition|trust_boundary|extension_point|diagnostic|dependency`, so it
needs **no change** for the new kinds (verified at `profiles/core000/schemas/claim.schema.json`).

Resulting counts: 12 reciprocal pairs (24 declarations) + 4 without an inverse = 28; cardinality
`one` on `startsAt`, `endsAt`, `loadedBy`, `raisedIn`; 24 `many`. `subject` remains the only
wildcard, so no wildcard inverse exists. Profile validation in `spec/lib/manifest.ts` accepts this
shape; the resolver in `spec/lib/relations.ts` synthesizes the inverse values.

Data rule: **declare forward edges only** in `structure.yml` (e.g. `provides` on the component,
`loadedBy` on the extension point, `concerns` on the trust boundary); `providedBy`, `loads`,
`guardedBy`, `requiredBy`, `exposedBy` are synthesized. Declaring both sides is legal but is not
needed in S2.1 and would add review surface.

## 6. Data flow and compatibility details

### 6.1 Pipeline position of S2.1

`runBuild` → manifest/profile load (new pointers, 14 kinds) → consent gate → profile closure
(28 files) → output containment → schema load (16 schemas) → document validation → extraction
(14 kinds) → identity/uniqueness → relations (28 declarations, reciprocal synthesis) → provenance
binding → `verifyProvenance` → `buildView` + `validate` (24 codes) + catalog resolution → renderer →
identity → one artifact → blocking/check/write. No step is added, skipped or reordered.

### 6.2 Reserved-name collision (blocking design detail)

`spec/lib/ir.ts` strips `id`, `kind`, `type`, `provenance`, `verification` and `relations` from
`entity.fields`. The accepted design requires `dependency.kind` and `conformance_case.kind` as data
fields, so their values are **not** present in `entity.fields`; `entity.kind` holds
`dependency`/`conformance_case` instead. The existing profile already solves the same problem for
`evidence.kind` with a bounded raw-document accessor (`evidenceKind` in `view.ts`, covered by an S1
test).

Proposed for S2.1: generalise that accessor in `view.ts` (for example
`documentField(model, documentKey, collection, id, field)`) and read `dependency.kind` from
`documents["structure"].dependencies` and `conformance_case.kind` from
`documents["claims"].conformanceCases`. The accessor fails closed on missing, duplicate or malformed
entries, as `evidenceKind` does. This needs no core change and no field rename; the alternative
(rename the data fields) would change accepted design field names and needs maintainer review (open
question 5).

The same accessor is **not** needed for `diagnostic.phase`/`dependency.status`/etc.; those are not
reserved.

### 6.3 Relation data shape

- `many` values may be strings or arrays of strings; data uses arrays for `provides`, `requires`,
  `exposes`, `concerns`.
- `one` values must be scalar strings: `startsAt`, `endsAt`, `loadedBy`, `raisedIn`. An array is
  `core.relation.cardinality`.
- Every `(from, name)` pair is unique; each inverse is declared from the forward `to` kind with
  reversed endpoints; no inverse is declared on `subject`.
- Inverse values are synthesized; an explicit inverse declaration in data is optional and omitted.

### 6.4 Trust-policy check scoping (conditional)

`profiles/core000/checks/trust-policy.ts` currently requires **every** trust boundary to be
`settled`/`explicit_consent` and otherwise emits `core000.trust.consent-facts`. The design §5.7 scopes
that rule to `TB-PROFILE-EXEC`. With only `TB-PROFILE-EXEC` in the data the over-broad check is
harmless, so S2.1 needs no change **if** no second trust boundary is added. If the maintainer answers
open question 2 by including `TB-CONSUMER-EXTENSION`, the check must be scoped to
`TB-PROFILE-EXEC` in the same PR (an existing code's semantics, not a new code).

### 6.5 View and template

`view.ts` gains six collections (`phases`, `transitions`, `extensionPoints`, `dependencies`,
`modelDiagnostics`, `conformanceCases` plus counts) and their view types; `buildView` returns them and
extends `counts`. `renderer.ts` needs **no** change: it spreads `buildView` into the template context
and does not enumerate fields. The template gains sections (Phases, Transitions, Extension points,
Dependencies, Diagnostic catalog, Conformance cases) and count entries; section names must not
collide with the existing "Build diagnostics" section, so the model entities render under
"Diagnostic catalog". `throwOnUndefined: true` means every template variable must exist on the view.

### 6.6 Expected S2.1 diagnostic set

With the proposed data: **0 errors, 3 reviews, 16 warnings = 19 diagnostics**.

- 3 reviews: `core000.independent-verification.missing` for `C000-TR-001` (human), `C000-TR-003`
  (external) and `C000-IM-004` (external) — unchanged from S1.
- 16 warnings: `core000.surface.claim-missing` for 6 components (`COMP-PROFILE`, `COMP-PROJECT`,
  `COMP-ADAPTER`, `COMP-RENDERER`, `COMP-CLI`, `COMP-REVIEWER`) and 10 interfaces
  (`IF-PROJECT-MODEL`, `IF-BUILD-IDENTITY`, `IF-DIAGNOSTIC`, `IF-BUILD-RESULT`, `IF-ADAPTER`,
  `IF-RENDERER`, `IF-CONFORMANCE`, `IF-CLI`, `IF-CONSENT-OPTION`, `IF-CONSENT-CLI-FLAG`).
- 0 warnings from `evidence.orphan` (all 8 evidence rows support a claim); 0 errors from
  `interface-owner-mismatch`, `evidence.locator` and the vacuous checks.

Warnings do not block a draft and are not converted to errors; S2.1 records the exact set. Release
stays blocked by the three reviews.

## 11. Stop conditions and risks

### 11.1 Stop conditions (do not improvise; report the blocker)

- A required model element needs a `spec/lib/` change or a new core capability (none found).
- A check needs I/O, a clock, the network or an environment value.
- A structural identifier has no defensible source (none at the model level; the uncertain
  encodings are open questions, not silent decisions).
- Any accepted decision would have to change, any claim would have to be promoted, or the five S1
  claims cannot be preserved.
- The S2.1 data would need a case from S2.3 or S3 to pass.
- The expected S2.1 diagnostic set cannot be made exact and testable.
- Any run writes to the repository, exposes a secret or cannot be cleaned up.

### 11.2 Risks

1. **Structural vocabulary is the main review surface.** 7 components, 12 interfaces, 9 phases, 8
   transitions, 4 extension points and 7 dependency rows are proposed encodings; the maintainer must
   confirm or amend them before implementation (open questions 1–5, 10).
2. **Reserved `kind`.** If the raw-document accessor is rejected, the model needs renamed fields, an
   accepted-design deviation and possibly a schema change (open question 5).
3. **Warning count depends on `public` flags and the interface list.** A change to either changes the
   hard-coded 16; the test must derive and assert the set, not just a count.
4. **Diagnostic duplication.** The 24 diagnostic entities duplicate catalog metadata by design; a
   drift between `catalog.json` and `structure.yml` is only caught by an S2.1 test, not by the engine.
5. **`trust.consent-facts` over-broad scope** becomes a bug the moment a second trust boundary exists
   (§6.4); S2.1 keeps one boundary, so the latent issue is documented rather than fixed.
6. **`evidence.locator`/`claim.invalid-status` partially duplicate schemas**, so their focused
   failing tests (S2.3) need in-memory or schema-bypassing inputs to be meaningful (open question 6).
7. **Phase/transition data may be read as new guarantees.** The proposal copies contract §6.1/§6.2
   text precisely so it restates accepted guarantees; any paraphrase in review should be rejected.
8. **Documentation count corrections touch planning records' forward-looking text only.** Historical
   S1 snapshots stay historical; a mechanical replacement would rewrite history and is out of scope.
