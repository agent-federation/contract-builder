## 4. Proposed S2.1 scope

### 4.1 Goal

Extend the existing five-claim S1 slice to the accepted model surface without changing generic-core
behaviour:

- 8 → 14 entity kinds;
- 11 → **29** relation declarations (the 28 accepted in the S2 package plus the owner-approved
  `hasPrerequisite` relation);
- 13 → 24 policy-check codes (S2-D1 A);
- S1 structure excerpt → the full public structure (components, interfaces, 9 phases, 8 phase
  prerequisites, zero transition instances, extension points, trust boundaries, diagnostics,
  dependencies);
- `conformance_case` kind/schema and manifest pointer with `conformanceCases: []`;
- preserve the five S1 claims, their statuses and their relations;
- 19 → 28 profile-closure files, 10 → 16 schemas.

### 4.2 Explicit non-goals

- No `spec/lib/` change, no new core capability, no CLI/API implementation, no G4 closure.
- No 78-claim register, no claim promotion, no regression of the five S1 claims (S2.2).
- No focused failing tests for the 11 new checks (S2.3); no N1–N18 matrix (S3).
- No durable evidence, no committed CORE-000 draft (Q9: the draft is planned for S2.2 and durable
  evidence/summary for S2.3; the transient harness record is still produced by tests).
- No H2/H3 result, no independent verification record, no sandbox/isolation claim.
- No change to the accepted design, execution plan or S2 package. The canonical decision record is
  updated only to record the owner decisions in this reconciliation.
- No change to `CORE-001.legacy.md`, `spec/`, `profiles/core001/`, `pap/`, `package.json` or
  `bun.lock`.

### 4.3 Later-stage artifact direction (Q9 A + staged D)

S2.1 commits nothing: the harness output is transient. The owner decision sets this planning
direction for later stages (not authorization to implement them):

- `contracts/core000/output/CORE-000.draft.md` — planned for **S2.2**, after the full claim register
  makes a successful reviewed run possible.
- `evidence/core000/<run>/result.json` and
  `docs/architecture/core-000-execution-evidence.md` — planned for **S2.3**, after the focused checks
  are available.
- Before either stage, specify a reproducible **copy-from-temporary-workspace** procedure (the
  harness intentionally refuses repository writes) and a **CORE-000-specific artifact verification**
  command/check. `bun run check` validates CORE-001 only and must not be cited as CORE-000 artifact
  verification.
- These are later-stage deliverables; S2.1 creates no artifacts and this document does not authorize
  S2.2/S2.3.

## 5. Proposed model surface

### 5.1 Entity kinds (14)

Existing eight remain; six are added. Fields are from design §5.3; all schemas keep the reserved
names (`id`, `kind`, `type`, `provenance`, `verification`, `relations`, `review`).

| Kind | Required fields (proposed schema) | Optional | Reserved-name note |
|---|---|---|---|
| `phase` | `id`, `name`, `guarantee`, `not_guaranteed` | `public` | — |
| `transition` | `id`, `condition`, `description` | — | phase endpoints via `startsAt`/`endsAt` relations |
| `dependency` | `id`, `name`, `kind`, `status` | `version`, `consequence` | `kind` is reserved and stripped: the value is read from the source document (see §6.2) |
| `extension_point` | `id`, `name`, `mechanism`, `trust`, `status` | `description` | — |
| `diagnostic` | `id`, `code`, `severity`, `phase`, `message`, `status` | `disposition`, `blocking` | — |
| `conformance_case` | `id`, `kind`, `input`, `expected`, `status` | `notes` | `kind` is reserved and stripped (see §6.2) |

ID patterns proposed for review: `^PH-[A-Z0-9-]+$`, `^TR-[A-Z0-9-]+$`, `^[a-z@][a-z0-9@._/-]*$`
(dependency = manifest name), `^EXT-[A-Z0-9-]+$`, `^(core000|core)\.[a-z0-9.-]+$` (diagnostic id =
catalog code), `^CC-[A-Z0-9-]+$`. Transition IDs are not used in S2.1; the `TR-` pattern is retained
for the kind.

`claim.schema.json` already declares `subject_kind` over
`component|interface|phase|transition|trust_boundary|extension_point|diagnostic|dependency`, so it
needs **no change** for the new kinds (verified at `profiles/core000/schemas/claim.schema.json`).

Resulting counts: 12 reciprocal pairs (24 declarations) + 5 without an inverse (`startsAt`, `endsAt`,
`subject`, `raisedIn`, `hasPrerequisite`) = 29; cardinality `one` on `startsAt`, `endsAt`,
`loadedBy`, `raisedIn`; 25 `many`. `subject` remains the only wildcard, so no wildcard inverse
exists. Profile validation in `spec/lib/manifest.ts` accepts this shape; the resolver in
`spec/lib/relations.ts` synthesizes the inverse values.

Data rule: **declare forward edges only** in `structure.yml` (e.g. `provides` on the component,
`loadedBy` on the extension point, `concerns` on the trust boundary, `hasPrerequisite` on the
dependent phase); `providedBy`, `loads`, `guardedBy`, `requiredBy`, `exposedBy` are synthesized.
Declaring both sides is legal but is not needed in S2.1 and would add review surface.

#### 5.4.3 Phases (9) — contract §6.1

| ID | Name | Guarantee (from contract §6.1) | Not guaranteed |
|---|---|---|---|
| `PH-LOAD` | load | bytes read, manifest parsed, profile resolved | content correctness |
| `PH-STRUCTURE` | structure | documents match input schemas; extracted entities match kind schemas | semantic meaning |
| `PH-REFERENCE` | reference | IDs unique, relations resolvable | that references are appropriate |

#### 5.4.4 Phase prerequisites (8) — Q1 decision

S2.1 encodes the lifecycle dependencies as `hasPrerequisite` edges (relation 29), not as transition
instances. The eight edges are the contract §6.2 prerequisites:

| Dependent phase | Prerequisites | Source |
|---|---|---|
| `PH-STRUCTURE` | `PH-LOAD` | §6.2 "structure requires load" |
| `PH-REFERENCE` | `PH-STRUCTURE` | §6.2 "reference requires structure" |
| `PH-PROVENANCE` | `PH-STRUCTURE` | §6.2 "provenance requires structure" |

| `PH-REVIEW` | `PH-STRUCTURE` | §6.2 "review requires structure" |
| `PH-CONFORMANCE` | `PH-STRUCTURE` | §6.2 "conformance requires structure" |
| `PH-ARTIFACT` | — (the build-success gate is result-level, not a phase prerequisite) | §6.2 "artifact requires a successful build" |

Data: `relations: { hasPrerequisite: [PH-…, …] }` on each dependent phase (array; cardinality `many`).

**Semantics (owner-approved 2026-11-03).** Each item is labelled as a repository fact, an approved
formalization, or a policy choice:

- **Approved formalization of `requires`** (not a consequence explicitly stated by §6.2): in a
  completed run, if a dependent phase is `passed` or `failed` (it was entered), every prerequisite is
  `passed` in that same run.
- **Eligibility** (definition): all prerequisites `passed` establishes eligibility only; it does not
  imply entry, execution or outcome. "Admitted", if used, means this eligibility predicate; there is
  no admission event.
- **Direct failure→skip** (the sentence is repository fact; "direct" is the owner-approved reading):
  §6.2 states that "a failing phase marks dependent phases `skipped`"; S2.1 reads this as the direct
  dependents, not a recursive rule.
- **Completeness rule** (owner-approved policy, distinct from §6.2): every declared phase has exactly
  one of the three existing states in a completed `BuildResult`; a phase not entered because a
  prerequisite is non-passed is recorded as `skipped`. This supplies the downstream/transitive
  result; it is not a recursive reading of §6.2.
- **Acyclicity** (owner-approved well-formedness policy): the `hasPrerequisite` graph must be
  acyclic. This is not derived from the invariant or non-vacuity; S2.1 enforces it by test only, with
  no new policy code and no generic-core rule.
- **No causal production rule**: `hasPrerequisite` encodes no execution order, timing, scheduler,
  admission event or state-production semantics.
- **Incomplete observations**: unknown/absent prerequisite knowledge belongs to incomplete or
  intermediate records only; a completed `BuildResult` has exactly the three existing states
  (contract §8). Unknown is not silently mapped to `skipped`; any fail-closed mapping is a separately
  labelled policy choice, not adopted here.
- **Empty prerequisite set**: vacuous eligibility (definitional).

## 6. Data flow and compatibility details

### 6.1 Pipeline position of S2.1

`runBuild` → manifest/profile load (new pointers, 14 kinds) → consent gate → profile closure
(28 files) → output containment → schema load (16 schemas) → document validation → extraction
(14 kinds) → identity/uniqueness → relations (29 declarations, reciprocal synthesis) → provenance
binding → `verifyProvenance` → `buildView` + `validate` (24 codes) + catalog resolution → renderer →
identity → one artifact → blocking/check/write. No step is added, skipped or reordered.

### 6.2 Reserved-name collision (reserved-name design detail)

`spec/lib/ir.ts` strips `id`, `kind`, `type`, `provenance`, `verification` and `relations` from
`entity.fields`. The accepted design requires `dependency.kind` and `conformance_case.kind` as data
fields, so their values are **not** present in `entity.fields`; `entity.kind` holds
`dependency`/`conformance_case` instead. The existing profile already solves the same problem for
`evidence.kind` with a bounded raw-document accessor (`evidenceKind` in `view.ts`, covered by an S1
test).

Q5 decision — bounded typed accessors:

- Preserve the generic IR reserved `Entity.kind` semantics and the domain fields
  `dependency.kind` / `conformance_case.kind`; do not rename them and do not change generic IR
  extraction.
- The profile exposes two **typed** accessors: `dependencyKind(model, id)` and
  `conformanceCaseKind(model, id)`. A shared private helper may back them; **no unrestricted
  raw-document accessor is exposed to renderers or templates**.
- They fail closed on: missing entity or source document; wrong entity kind; missing or duplicate
  source record; malformed record; missing or invalid domain `kind`. They never fall back to
  `Entity.kind` or a default value.
- Only the resolved value reaches the view/template; templates never read `model.documents`.
  `evidenceKind` keeps its existing bounded role.
- This needs no core change and no field rename. The earlier idea of a generalized
  `documentField` accessor is **superseded** by the typed pair.
- Focused tests cover valid values, missing records, duplicate records, malformed records and
  invalid enum values (test plan T16).

The typed accessors are **not** needed for `diagnostic.phase`/`dependency.status`/etc.; those are
not reserved.

### 6.3 Relation data shape

- `many` values may be strings or arrays of strings; data uses arrays for `provides`, `requires`,
  `exposes`, `concerns`, `hasPrerequisite`.
- `one` values must be scalar strings: `startsAt`, `endsAt`, `loadedBy`, `raisedIn`. No `one`
  relation carries data in S2.1 (zero transition instances); an array is
  `core.relation.cardinality`.
- Every `(from, name)` pair is unique; each inverse is declared from the forward `to` kind with
  reversed endpoints; no inverse is declared on `subject`.
- Inverse values are synthesized; an explicit inverse declaration in data is optional and omitted.

### 6.4 Trust-policy check scoping (Q2, required)

`profiles/core000/checks/trust-policy.ts` currently requires **every** trust boundary to be
`settled`/`explicit_consent` and otherwise emits `core000.trust.consent-facts`. Design §5.7 scopes
that rule to `TB-PROFILE-EXEC` only. Q2 makes the correction **required**: the boundary loop is
scoped to `TB-PROFILE-EXEC`, so a non-profile boundary with `enforcement: none` (including
`TB-CONSUMER-EXTENSION`) does not produce that finding. Add a test for the scoped behavior.

`core000.trust.consent-facts` is a **review** diagnostic, not an error: an additional finding would
not fail the positive draft build; it would change the review set and affect release gating (release
is already blocked). The change inventory previously said "fail the positive build"; that statement
is corrected.

### 6.5 View and template

`extensionPoints`, `dependencies`, `modelDiagnostics`, `conformanceCases` plus counts), their view
