# CORE-000 S2.1 open questions

**Status:** planning-only. Unresolved questions requiring maintainer input before S2.1 implementation
is authorized. Baseline: `8d881d410c9945f7f5925fbf5772b06be2e9cc120`.
**Do not resolve these on the maintainer's behalf.** Each entry gives the exact question, the
repository evidence, viable options, the recommended option where one is justified, the consequence
of each choice, and whether it blocks S2.1.

A question marked **blocking** stops the affected encoding step; it does not authorize a speculative
default and does not stop unrelated S2.1 preparation (schemas that all options share, tests that
assert the accepted decisions). No question blocks the proposal package itself.

## Q1 — Phase and transition vocabulary: contract §6.1/§6.2 or the S2 package's 8-phase chain?

**Question.** Which phase and transition set should S2.1 encode: the public contract's 9 phases and
its dependency edges (including `conformance`), or the S2 package's 8-phase linear chain without
`conformance`?

**Repository evidence.**
- `engine-public-contract.md` §6.1 declares
  `load | structure | reference | provenance | verification | consistency | review | conformance | artifact`
  with a guarantee and a non-guarantee per phase.
- `engine-public-contract.md` §6.2 defines dependencies: `structure` requires `load`; `reference`,
  `provenance`, `verification`, `consistency`, `review`, `conformance` require `structure`;
  `verification` requires `provenance`; `artifact` requires a successful build.
- Design §5.9 names `PH-STRUCTURE`, `PH-REFERENCE` and `TR-STRUCTURE-REFERENCE` as examples only.
- S2 package §4.4 lists 8 phases (no `PH-CONFORMANCE`) and a 7-transition chain
  (`TR-LOAD-STRUCTURE` → … → `TR-REVIEW-ARTIFACT`), which is the M1 pipeline order, not §6.2.
- The M1 pipeline order is in execution plan §4 steps 1–16.

**Viable options.**
- **A (proposal default):** 9 phases from contract §6.1, guarantee strings restated from the contract
  table; 8 transitions for the §6.2 edges plus `TR-REVIEW-ARTIFACT` for the pipeline-order edge into
  the artifact phase. No new guarantee is invented; `PH-CONFORMANCE` is a modelled phase, not an
  execution claim.
- **B:** the S2 package's 8 phases and 7-transition chain, described explicitly as the M1 pipeline
  order rather than the contract's phase graph. Smaller, matches the planning package, but omits a
  contract phase and mislabels the chain as the §6.2 graph.
- **C:** 8 phases and the §6.2 edges among them (no conformance phase or edge).
- **D:** defer phases/transitions to a later stage and encode only the other new kinds.

**Recommended:** **A.** The public contract is the stronger accepted source for the engine lifecycle,
`conformance_case` is already in the 14-kind model, and restating the contract's guarantee cells
avoids inventing guarantees. `TR-REVIEW-ARTIFACT` is the one edge that is pipeline order rather than a
§6.2 dependency and should be labelled as such.

**Consequences.** A replaces three of the S2 package's transition IDs with four contract-edge IDs
and adds `PH-CONFORMANCE`; B keeps the S2 package wording but leaves the contract graph
unrepresented; C drops the contract's conformance phase; D leaves the transition relation and phase
kind without project data.

**Blocks S2.1:** yes — the structure-data step and the exact view/test counts. Not the schema/profile
work.

## Q2 — Include `TB-CONSUMER-EXTENSION` or omit it?

**Question.** Should the full public structure contain a second trust boundary for consumer-supplied
renderers/adapters (`TB-CONSUMER-EXTENSION`), or is the consumer extension boundary represented only
by the extension-point trust class?

**Repository evidence.**
- No accepted source names a `TB-CONSUMER-EXTENSION` entity. Design §5.9 lists only
  `TB-PROFILE-EXEC`; the current `structure.yml` has only that row.
- Design §6.2 records "Consent to consumer-imported adapters/renderers: No — the consumer's own
  import is its trust decision; the CLI gates only its profile renderer".
- Decision record P-5 §12 and execution plan §4.1 say the consumer-supplied renderer is a separate
  consumer trust boundary, not gated by `allowExecutableProfile`.
- Design §5.3 gives `extension_point.trust` the value `trusted_consumer_supplied`, so the trust class
  is already representable on `EXT-RENDERER`/`EXT-ADAPTER`.
- `profiles/core000/checks/trust-policy.ts` requires **every** trust boundary to be
  `settled`/`explicit_consent` and otherwise emits `core000.trust.consent-facts`; design §5.7 scopes
  that rule to `TB-PROFILE-EXEC`.

**Viable options.**
- **A (proposal default):** omit the entity; represent the consumer boundary on `EXT-RENDERER`
  (`trusted_consumer_supplied`) and `EXT-ADAPTER`. No new structural ID, no trust-check change, and
  no risk of conflating consumer trust with the executable-profile consent gate.
- **B:** add `TB-CONSUMER-EXTENSION` with `enforcement: none`, `policy_status: settled` and a
  statement that the consumer's import is its own trust decision; scope
  `core000.trust.consent-facts` to `TB-PROFILE-EXEC` in the same PR.
- **C:** defer the question and add neither the entity nor the documentation note.

**Recommended:** **A.** It matches the accepted sources (no named entity), keeps the trust
vocabulary on the extension point, and avoids changing an existing check's scope in S2.1. B is
defensible but needs the check-scope fix and a new structural identifier confirmed by the maintainer.

**Consequences.** A leaves the consumer boundary out of the trust-boundary section of the artifact;
B makes it visible but requires the check change and a data row whose `enforcement` value (`none`)
contradicts the current global rule; C is A without the recorded rationale.

**Blocks S2.1:** no with A; yes with B (the trust-check change and an extra row change the expected
diagnostic set and the structure schema data).

## Q3 — D14 consent surface: which interface IDs, and where does the `core.profile.consent-required` diagnostic entity live?

**Question.** What are the exact identifiers and list placement for the two consent interfaces and
the core-owned consent diagnostic entity that D14 A mandates?

**Repository evidence.**
- Decision record §4 (D14 A): "add interface entities for `allowExecutableProfile` and the CLI flag,
  a diagnostic entity for `core.profile.consent-required`, and keep `TB-PROFILE-EXEC`
  settled/`explicit_consent`".
- The implementation facts: `BuildOptions.allowExecutableProfile` defaults false; the CLI flag is
  `--allow-executable-profile`; absent consent fails closed with `core.profile.consent-required`
  before import (`spec/lib/build.ts`, `spec/build.ts`, `spec/cli-renderers.ts`,
  `tests/consent.test.ts`).
- S2 package §4.4 lists 10 interfaces and 24 diagnostics and does not include these rows.
- The design's §5.7 notes that `core.profile.consent-required` is a core-owned code and that core
  codes remain core-owned; the profile catalog declares only `core000.*` codes.
- The `diagnostic` entity has `id` and `code` fields; the diagnostic list is a single
  `/diagnostics` array in the manifest shape.

**Viable options.**
- **A (proposal default):** `IF-CONSENT-OPTION` (surface `api`, owner `COMP-CORE`, stability
  `accepted`) and `IF-CONSENT-CLI-FLAG` (surface `cli`, owner `COMP-CLI`, stability `accepted`);
  diagnostic entity `id` = `code` = `core.profile.consent-required`, `severity: error`,
  `phase`/`raisedIn` = `PH-LOAD`. The 24-code policy set is asserted by the `core000.` prefix, so the
  core-owned row is visible but outside the catalog reconciliation.
- **B:** put the consent diagnostic in a separate project list/pointer (`/coreDiagnostics`) so the
  `/diagnostics` list stays exactly 24.
- **C:** omit the diagnostic entity and describe the consent diagnostic only in the interface/trust
  rows (contradicts D14 A).

**Recommended:** **A.** It satisfies D14 literally, needs no new document or pointer, and keeps one
diagnostic inventory. The cost is 25 rows where 24 are catalog codes; the prefix assertion makes the
distinction testable.

**Consequences.** A adds two interface rows, both unclaimed, so the total becomes 16
warnings and the diagnostic count to 25. B keeps "24 diagnostics" but
adds an undocumented second list and a new manifest pointer. C leaves an accepted decision
unrepresented.

**Blocks S2.1:** yes — it fixes the interface and diagnostic counts the tests assert.

## Q4 — Diagnostic entity identity and `status` vocabulary

**Question.** How is a `diagnostic` entity identified, and what values may its `status` field take?

**Repository evidence.**
- Design §5.3 requires `id`, `code`, `severity`, `phase`, `message`, `status` for `diagnostic`;
  it enumerates no `status` values (unlike claim status, dependency status and conformance-case
  status, whose enums are given).
- S2 package §4.4 says "all 24 catalog codes, each with code, severity, phase and status".
- The catalog `code` is already the stable identifier (`catalog.json`); the design says diagnostic
  codes are a stable public surface (design §5.2).
- Every other kind has a kind-prefixed `id` pattern; a diagnostic `id` = code would be the only
  non-prefixed identity.

**Viable options.**
- **A (proposal default):** `id` = `code` (for example `core000.claim.invalid-status`), schema
  pattern `^(core000|core)\.[a-z0-9.-]+$`; `status` is a free non-empty string in S2.1, data uses
  `declared`. The catalog remains the message/severity authority; a test asserts entity/catalog
  equality.
- **B:** kind-prefixed IDs (`DIA-INVALID-STATUS`) plus `code`, requiring a stable ID-to-code mapping
  not present in any accepted source.
- **C:** closed `status` enum (`declared`/`implemented`/`verified`) invented in S2.1.

**Recommended:** **A.** `id` = `code` avoids a parallel vocabulary and makes the 24-code
reconciliation a set comparison; leaving `status` open avoids inventing a closed vocabulary the design
does not define. B invents an ID scheme; C invents an enum.

**Consequences.** A makes `id` and `code` duplicate for these rows (accepted as an explicit review
item) and defers the enum. B is cleaner-looking but unsourced. C adds normative vocabulary without a
decision.

**Blocks S2.1:** no with A. The maintainer should confirm A before the S2.1 data is frozen; B or C
would require a new vocabulary and would block.

## Q5 — Reserved-name collision: `dependency.kind` and `conformance_case.kind`

**Question.** How should S2.1 represent the design-required `kind` fields on `dependency` and
`conformance_case`, given that the generic core reserves and strips `kind`?

**Repository evidence.**
- `spec/lib/ir.ts` strips `id`, `kind`, `type`, `provenance`, `verification`, `relations` from
  `entity.fields`; `entity.kind` holds the entity kind (`dependency`/`conformance_case`), so a data
  value such as `runtime` or `positive` is not in `entity.fields`.
- Design §5.3 requires `dependency.kind` (`runtime`/`toolchain`/`pipeline`/`decision`/`product`) and
  `conformance_case.kind` (`positive`/`negative`).
- The same problem already exists for `evidence.kind`; the profile solves it with a bounded
  raw-document accessor (`evidenceKind` in `profiles/core000/view.ts`, tested in
  `tests/core000.test.ts` "S1 evidence kind").
- `review` is allowed in `fields`; `kind` is not.

**Viable options.**
- **A (proposal default):** keep the accepted field names and generalise the existing accessor to
  read `dependency.kind` from `documents["structure"].dependencies` and `conformance_case.kind` from
  `documents["claims"].conformanceCases`, failing closed on missing/duplicate/malformed entries.
- **B:** rename the data fields (`dependency_kind`, `case_kind`) in schema and data.
- **C:** drop the field from the S2.1 data and rely on `entity.kind`/`subject_kind`.

**Recommended:** **A.** It preserves the accepted design field names, reuses a tested profile
pattern, and needs no core change. B changes accepted field names and needs a documented design
deviation; C loses accepted information.

**Consequences.** A adds a small view accessor and one S2.1 test (S2.1-T16). B needs an accepted
design amendment and schema/template changes. C makes the dependency rows indistinguishable by kind.

**Blocks S2.1:** yes — it fixes the schema and view shape.

## Q6 — `claim.invalid-status` and `evidence.locator` partly duplicate schema constraints

**Question.** How should S2.1 implement two accepted checks whose "at least one" conditions are
already enforced by the entity schemas?

**Repository evidence.**
- `claim.schema.json` already enumerates `status.decision`, `.implementation`, `.tests`,
  `.verification`; an invalid status fails `core.schema.entity` before the validator hook runs.
- `evidence.schema.json` already requires `locator` and `revision` with `minLength: 1`.
- Design §5.7 states the rules: "Status values are in the §5.3.1 enums" and "Evidence locator is
  non-empty and has a path/URL/command form; revision is non-empty".
- The S2 package §5.3 expects both codes to have focused failing tests in S2.3.

**Viable options.**
- **A (proposal default):** implement both as defensive profile checks that re-assert the design
  rules on the model (status enums; non-empty trimmed locator/revision) without inventing a new
  path/URL/command grammar. Their S2.3 focused tests use in-memory models, which is allowed for
  synthetic check inputs.
- **B:** define a path/URL/command regex now and enforce it.
- **C:** omit both checks as schema-redundant (departs from the 24-code set).

**Recommended:** **A.** It keeps all 24 accepted codes without adding normative grammar in S2.1.
B is defensible later but would make the check reject locators the design does not forbid; C breaks
S2-D1 A.

**Consequences.** A leaves the two checks partly redundant with the schemas; that redundancy is
documented, and S2.3 must exercise them with in-memory models. B risks false rejections on future
locators. C changes the normative check set.

**Blocks S2.1:** no with A.

## Q7 — `claim.status-class-conflict` and the limitation exception

**Question.** How is the design rule "`a limitation` cannot carry `decision: accepted` unless it
restates an accepted limitation" enforced without inventing a marker?

**Repository evidence.**
- Design §5.7 gives the rule with the exception; no accepted source defines a field that marks
  "restates an accepted limitation".
- The accepted register contains limitations with accepted decisions (for example `C000-TR-004`,
  `C000-LM-005`), so a check that flags `limitation` + `accepted` would reject valid accepted rows
  once the full register lands (S2.2).
- The deterministic parts of the rule are `non_goal`/`deferred` cannot be implemented or tested and
  `proposal` cannot be implemented.

**Viable options.**
- **A (proposal default):** enforce only the deterministic parts; allow `limitation` +
  `accepted` and record the exception as a review-level documentation note in the check's comment,
  not as a new code.
- **B:** add a marker field (for example `restates_accepted_limitation`) and enforce the full rule.
- **C:** enforce the literal rule and exclude accepted limitations from the check by ID list.

**Recommended:** **A.** It enforces what is machine-checkable now and avoids either a new field
(B, new vocabulary/decision) or a hard-coded ID list (C, a parallel register).

**Consequences.** A narrows one accepted code's reach for limitations; B and C add unaccepted
structure. The narrowing should be stated in the S2.3 test notes.

**Blocks S2.1:** no with A.

## Q8 — Dependency rows and their kind mapping

**Question.** Which dependency rows does S2.1 encode, and with what `kind` values?

**Repository evidence.**
- `package.json`: `packageManager: "bun@1.4.2"`, `engines.bun: ">=1.4.0"`, dependencies `ajv`,
  `nunjucks`, `yaml`, devDependencies `@types/node`, `@types/nunjucks`, `typescript`.
- `bun.lock` pins the exact versions; `jiti`/`commander`/`chokidar` are transitive entries, not
  declared manifest dependencies.
- Design §5.3: dependency `kind` is `runtime`/`toolchain`/`pipeline`/`decision`/`product`; `status`
  is `declared`/`resolved`/`pending`/`deferred`/`not_applicable`.
- S2 package §4.4: "S2.1 must choose manifest-name IDs"; no accepted source fixes a dependency list.

**Viable options.**
- **A (proposal default):** the 7 manifest names (`bun`, `ajv`, `nunjucks`, `yaml`, `typescript`,
  `@types/node`, `@types/nunjucks`) as IDs; `bun` = runtime/`declared`; `ajv`/`nunjucks`/`yaml` =
  runtime/`resolved`; `typescript`/`@types/*` = toolchain/`resolved`; `requires` edges from
  `COMP-CORE` (`bun`, `ajv`, `yaml`) and `COMP-RENDERER` (`nunjucks`).
- **B:** add pipeline/decision/product rows (for example `bun test`, `DEC-PR-56`, PAP) derived from
  prose rather than manifest names.
- **C:** encode no dependency rows.

**Recommended:** **A.** It follows the manifest-name rule exactly, is auditable against
`package.json`/`bun.lock`, and does not invent a parallel vocabulary. The unused toolchain rows are
honest; no check requires every dependency to be required by a component.

**Consequences.** A models only declared packages; B risks unsourced rows; C leaves the `requires`
relation and the dependency kind without project data.

**Blocks S2.1:** no with A.

## Q9 — Does S2.1 commit durable evidence or the generated draft?

**Question.** Should the S2.1 PR create `evidence/core000/<run>/result.json` and commit
`contracts/core000/output/CORE-000.draft.md`, given that P-2/P-3/P-6 are accepted for S2?

**Repository evidence.**
- The decision record accepts P-2 A and P-3 A for the full-model planning scope; P-3 says "after a
  successful, reviewed run".
- S2 package §5.1 (S2.1) lists no evidence or draft path; §5.2 (S2.2) and §5.3 (S2.3) carry them.
- No `evidence/` or `contracts/core000/output/` directory exists at the baseline.
- S2.1 does not produce the full model; a committed partial draft would be a misleading artifact.

**Viable options.**
- **A (proposal default):** no durable evidence and no committed draft in S2.1; tests still produce
  and assert the transient harness record.
- **B:** commit S2.1 evidence and the S2.1 draft alongside the stage.
- **C:** commit the draft only, no evidence.

**Recommended:** **A.** It follows the S2 package's staging and avoids presenting a partial model as
the full draft. B/C would need a maintainer decision on committing stage artifacts.

**Consequences.** A defers the P-2/P-3 deliverable to S2.2/S2.3; B/C create reviewable but
easily-mistaken artifacts.

**Blocks S2.1:** no.

## Q10 — Structure rows, `public` flags and the exact expected warning set

**Question.** Confirm the proposed structure rows and `public` flags, and the resulting exact expected
positive diagnostic set (3 review + 16 warning), or name the rows that change.

**Repository evidence.**
- S2 package §4.4 proposes 7 components, 10 interfaces, 8 phases, 7 transitions, 4 extension points,
  `TB-PROFILE-EXEC`, 24 diagnostics, dependencies and no conformance cases.
- The current `structure.yml` marks only `COMP-CORE` and the three interfaces; `public` is required on
  components and absent on interfaces.
- Design §5.7 defines `core000.surface.claim-missing` as "Every public component/interface has at
  least one claim"; the accepted design does not say which components are public.
- The five S1 claims cover `COMP-CORE`, `IF-MANIFEST`, `IF-PROFILE-VALIDATOR` and `TB-PROFILE-EXEC`
  only, so any set of public surfaces larger than that produces warnings.

**Viable options.**
- **A (proposal default):** all 7 components `public: true`; 12 interfaces (all treated as public);
  16 warnings; 3 reviews; total 19.
- **B:** mark non-contract components (for example `COMP-PROJECT`, `COMP-REVIEWER`) `public: false`,
  reducing the warning count.
- **C:** treat "public interface" as a `stability: accepted` filter instead of "every interface".

**Recommended:** **A.** CORE-000 describes its public contract, the design's component row lists all
seven as public responsibility units, and an interface has no `public` field in the accepted schema.
The 16 warnings are the honest consequence of the five-claim slice; S2.2 must reduce or account for
them.

**Consequences.** A fixes the expected count at 19 and gives S2.2 a concrete target; B hides real
uncovered surfaces behind a flag not required by the design; C invents a public filter the design
does not define.

**Blocks S2.1:** yes — the exact expected code set is an S2.1 acceptance criterion.
