## Q1 — Phase and transition semantics — RESOLVED by owner decision (2026-11-03)

**Status:** resolved. The project owner confirmed the Q1 decisions on 2026-11-03 (PR #87
discussion). This record preserves the outcome; it is not an implementation authorization.

**Decision (owner-approved).**

1. **`requires` formalization.** The normative formalization is the post-run invariant: in a completed
   run, if a dependent phase is `passed` or `failed` (it was entered), every prerequisite is `passed`
   in that same run. This is labelled the maintainer-approved formalization of `requires`; it is
   **not** a consequence explicitly stated by contract §6.2.
2. **Eligibility terminology.** "All prerequisites `passed`" establishes eligibility only; it does not
   imply entry, execution or outcome. "Admitted", if used, means eligibility; admission is not an
   event.
3. **Skip semantics.** §6.2's failure-to-skip rule is read directly (owner-approved reading): a
   failing phase marks its **direct** dependents `skipped`. The contract text says "dependent
   phases"; "direct" is the adopted reading, and recursive propagation is not attributed to §6.2. For completed
   `BuildResult` records, the adopted completeness rule is that every declared phase has exactly one
   of the three existing states; a phase not entered because a prerequisite is non-passed is recorded
   as `skipped`. The completeness rule is a separate approved policy and supplies the
   downstream/transitive result without being misattributed to §6.2.
4. **Acyclicity.** An acyclic `hasPrerequisite` graph is required as an explicit well-formedness
   policy. It is not derived from the run-level invariant or from non-vacuity. It is enforced by the
   S2.1 test only; no policy code and no generic-core rule are added.
5. **Causal state production.** No causal state-production rule is added to the relation or claimed as
   part of the current semantics. `hasPrerequisite` encodes no execution-order, timing, scheduler,
   admission-event or state-production semantics.
6. **Incomplete observations.** Unknown/absent knowledge is scoped to incomplete or intermediate
   observations. There is no fourth `PhaseState` and no fourth completed-`BuildResult` state.
   Unknown is not silently mapped to `skipped`; any fail-closed mapping remains a separately labelled
   policy choice.

**Scope kept.** One `hasPrerequisite` relation (phase → phase, many, no inverse) carrying the eight
contract §6.2 edges; zero transition instances; the M1 declared sequence remains authoritative in the
execution plan; the artifact build-success gate remains result-level.

**Repository evidence.**
- `engine-public-contract.md` §6.1 declares 9 phases and `PhaseState = passed | failed | skipped`.
- §6.2 states the prerequisites and that "a failing phase marks dependent phases `skipped`".
- §8/§9 define `BuildResult.phases: Record<Phase, PhaseState>`.
- The diagnostic `phase` field is deferred (`C000-CT-008`), so runtime phase execution is not
  observable at this baseline.

**Classification.** Facts: the §6.2 prerequisite list, the failure→skip sentence, the three phase
states, the public `phases` shape. Owner-approved formalization: the post-run invariant.
Owner-approved reading/policies: the direct reading of the failure→skip sentence, the completeness
rule and acyclicity. Definitional: eligibility, empty-set vacuous eligibility. Not adopted: any causal
state-production rule, any execution-order/scheduler semantics, any fourth phase state.

**Deferred.** Runtime verification of eligibility/skip (needs phase observability), any future
transition/permitted-move graph and its source, and any change to the completeness/acyclicity
policies.

**Blocks S2.1:** no — resolved.

## Q2 — Include `TB-CONSUMER-EXTENSION` or omit it?

**Question.** Should the full public structure contain a second trust boundary for consumer-supplied
renderers/adapters (`TB-CONSUMER-EXTENSION`), or is the consumer extension boundary represented only
by the extension-point trust class?

**Repository evidence.**
- No accepted source names a `TB-CONSUMER-EXTENSION` entity. Design §5.9 lists only
  `TB-PROFILE-EXEC`; the current `structure.yml` has only that row.
- Design §6.2 table: "Consent to consumer-imported adapters/renderers | No | The consumer's own
  import is its trust decision; the CLI gates only its profile renderer."
- Decision record §12 (consumer harness) and execution plan §4.1 say the consumer-supplied renderer
  is a separate consumer trust boundary, not gated by `allowExecutableProfile`.
- Design §5.3 gives `extension_point.trust` the value `trusted_consumer_supplied`, so the trust class
  is already representable on `EXT-RENDERER`/`EXT-ADAPTER`.
- `profiles/core000/checks/trust-policy.ts` requires **every** trust boundary to be
  `settled`/`explicit_consent` and otherwise emits `core000.trust.consent-facts`; design §5.7 scopes
  that rule to `TB-PROFILE-EXEC`.

**Viable options.**
- **A (proposal default):** omit the entity; represent the consumer boundary on `EXT-RENDERER`
  (`trusted_consumer_supplied`) and `EXT-ADAPTER`. No new structural ID, no trust-check change, and
  no risk of conflating consumer trust with the executable-profile consent gate.
- **B:** add `TB-CONSUMER-EXTENSION` with `enforcement: none`, `policy_status: settled` and a
  statement that the consumer's import is its own trust decision; scope
  `core000.trust.consent-facts` to `TB-PROFILE-EXEC` in the same PR.
- **C:** defer the question and add neither the entity nor the documentation note.

**Recommended:** **A.** It matches the accepted sources (no named entity), keeps the trust
vocabulary on the extension point, and avoids changing an existing check's scope in S2.1. B is
defensible but needs the check-scope fix and a new structural identifier confirmed by the maintainer.

**Consequences.** A leaves the consumer boundary out of the trust-boundary section of the artifact;
B makes it visible but requires the check change and a data row whose `enforcement` value (`none`)
contradicts the current global rule; C is A without the recorded rationale.

**Blocks S2.1:** no with A; yes with B (the trust-check change and an extra row change the expected
diagnostic set and the structure schema data).

## Q3 — D14 consent surface and diagnostic ownership — RESOLVED by owner decision (2026-11-04)

**Status:** resolved. Owner decision **Q3 = A**, with an explicit schema clarification.

**Decision (owner-approved).**

1. Consent surface: `IF-CONSENT-OPTION` for `BuildOptions.allowExecutableProfile`,
   `IF-CONSENT-CLI-FLAG` for `--allow-executable-profile`, and diagnostic entity
   `core.profile.consent-required`.
2. `TB-PROFILE-EXEC` stays settled with `enforcement: explicit_consent`; no sandboxing or process
   isolation is implied.
3. The consent diagnostic is **core-owned**, not a CORE-000 profile diagnostic.
4. One `/diagnostics` inventory: 24 profile-owned `core000.*` entries matching the profile catalog,
   plus one core-owned `core.profile.consent-required`; expected total **25**.
5. The model-level `diagnostic` schema is preserved: `phase` remains required under design §5.3; the
   consent diagnostic is associated with `PH-LOAD`; if `raisedIn` is represented it must agree with
   `phase`; D14's deferral of the **runtime** `disposition`/`phase` fields does not remove or
   redefine model-level fields.

Do not introduce a second diagnostic inventory or infer diagnostic ownership solely from code
prefixes.

**Repository evidence.** Decision record §4 (D14 A); `catalog.json` (24 codes); design §5.3
(diagnostic fields); `C000-CT-008` (runtime diagnostic shape deferred); contract §8
(`BuildResult.phases`).

**Consequence for Q4.** Q4 (diagnostic `id` and `status`) remains open only for that vocabulary;
diagnostic ownership is now fixed by **catalog membership**, not by a prefix.

**Newly discovered contradiction:** none. The core-owned row in the model-level inventory is
compatible with the runtime-shape deferral because the model-level `phase` is a declaration, not a
runtime diagnostic field.

**Blocks S2.1:** no — resolved.

## Q4 — Diagnostic entity identity and `status` vocabulary

**Question.** How is a `diagnostic` entity identified, and what values may its `status` field take?
(Q3, resolved 2026-11-04, fixes diagnostic ownership by catalog membership; this question covers only
the `id` and `status` vocabulary.)

**Repository evidence.**
- Design §5.3 requires `id`, `code`, `severity`, `phase`, `message`, `status` for `diagnostic`;
  it enumerates no `status` values (unlike claim status, dependency status and conformance-case
  status, whose enums are given).
- S2 package §4.4 says "all 24 catalog codes, each with code, severity, phase and status".
- The catalog `code` is already the stable identifier (`catalog.json`); the design says diagnostic
  codes are a stable public surface (design §5.2).
- Every other kind has a kind-prefixed `id` pattern; a diagnostic `id` = code would be the only
  non-prefixed identity.

**Viable options.**
- **A (proposal default):** `id` = `code` (for example `core000.claim.invalid-status`), schema
  pattern `^(core000|core)\.[a-z0-9.-]+$`; `status` is a free non-empty string in S2.1, data uses
  `declared`. The catalog remains the message/severity authority; a test asserts entity/catalog
  equality.
- **B:** kind-prefixed IDs (`DIA-INVALID-STATUS`) plus `code`, requiring a stable ID-to-code mapping
  not present in any accepted source.
- **C:** closed `status` enum (`declared`/`implemented`/`verified`) invented in S2.1.

**Recommended:** **A.** `id` = `code` avoids a parallel vocabulary and makes the 24-code
reconciliation a set comparison; leaving `status` open avoids inventing a closed vocabulary the design
does not define. B invents an ID scheme; C invents an enum.

**Consequences.** A makes `id` and `code` duplicate for these rows (accepted as an explicit review
item) and defers the enum. B is cleaner-looking but unsourced. C adds normative vocabulary without a
decision.

**Blocks S2.1:** no with A. The maintainer should confirm A before the S2.1 data is frozen; B or C
would require a new vocabulary and would block.

## Q5 — Reserved `kind` and domain-field access — RESOLVED by owner decision (2026-11-04)

**Status:** resolved. Owner decision **Q5 = A**, with bounded typed accessors.

**Decision (owner-approved).**

1. Preserve the generic IR reserved `Entity.kind` semantics.
2. Preserve the domain fields `dependency.kind` and `conformance_case.kind`; do not rename them and do
   not change generic IR extraction.
3. Provide profile-level typed accessors `dependencyKind(model, id)` and
   `conformanceCaseKind(model, id)`; a shared private helper is acceptable. Do not expose an
   unrestricted raw-document accessor to renderers or templates.
4. Accessors fail closed on: missing entity or source document; wrong entity kind; missing or
   duplicate source record; malformed record; missing or invalid domain `kind`.
5. Do not fall back to `Entity.kind` or silently substitute a default value.
6. Focused tests cover valid values, missing records, duplicate records, malformed records and
   invalid enum values.

**Repository evidence.** `spec/lib/ir.ts` reserves `kind`; design §5.3 names the domain fields; the
existing `evidenceKind` accessor is the bounded precedent; the earlier generalized `documentField`
idea is superseded by the typed pair.

**Blocks S2.1:** no — resolved.

## Q6 — `claim.invalid-status` and `evidence.locator` partly duplicate schema constraints

**Question.** How should S2.1 implement two accepted checks whose "at least one" conditions are
already enforced by the entity schemas?

**Repository evidence.**
- `claim.schema.json` already enumerates `status.decision`, `.implementation`, `.tests`,
  `.verification`; an invalid status fails `core.schema.entity` before the validator hook runs.
- `evidence.schema.json` already requires `locator` and `revision` with `minLength: 1`.
- Design §5.7 states the rules: "Status values are in the §5.3.1 enums" and "Evidence locator is
  non-empty and has a path/URL/command form; revision is non-empty".
- The S2 package §5.3 expects both codes to have focused failing tests in S2.3.

**Viable options.**
- **A (proposal default):** implement both as defensive profile checks that re-assert the design
  rules on the model (status enums; non-empty trimmed locator/revision) without inventing a new
  path/URL/command grammar. Their S2.3 focused tests use in-memory models, which is allowed for
  synthetic check inputs.
- **B:** define a path/URL/command regex now and enforce it.
- **C:** omit both checks as schema-redundant (departs from the 24-code set).

**Recommended:** **A.** It keeps all 24 accepted codes without adding normative grammar in S2.1.
B is defensible later but would make the check reject locators the design does not forbid; C breaks
S2-D1 A.

**Consequences.** A leaves the two checks partly redundant with the schemas; that redundancy is
documented, and S2.3 must exercise them with in-memory models. B risks false rejections on future
locators. C changes the normative check set.

**Blocks S2.1:** no with A.

## Q7 — `claim.status-class-conflict` and the limitation exception

**Question.** How is the design rule "`a limitation` cannot carry `decision: accepted` unless it
restates an accepted limitation" enforced without inventing a marker?

**Repository evidence.**
- Design §5.7 gives the rule with the exception; no accepted source defines a field that marks
  "restates an accepted limitation".
- The accepted register contains limitations with accepted decisions (for example `C000-TR-004`,
  `C000-LM-005`), so a check that flags `limitation` + `accepted` would reject valid accepted rows
  once the full register lands (S2.2).
- The deterministic parts of the rule are `non_goal`/`deferred` cannot be implemented or tested and
  `proposal` cannot be implemented.

**Viable options.**
- **A (proposal default):** enforce only the deterministic parts; allow `limitation` +
  `accepted` and record the exception as a review-level documentation note in the check's comment,
  not as a new code.
- **B:** add a marker field (for example `restates_accepted_limitation`) and enforce the full rule.
- **C:** enforce the literal rule and exclude accepted limitations from the check by ID list.

**Recommended:** **A.** It enforces what is machine-checkable now and avoids either a new field
(B, new vocabulary/decision) or a hard-coded ID list (C, a parallel register).

**Consequences.** A narrows one accepted code's reach for limitations; B and C add unaccepted
structure. The narrowing should be stated in the S2.3 test notes.

**Blocks S2.1:** no with A.

## Q8 — Dependency rows and their kind mapping

**Question.** Which dependency rows does S2.1 encode, and with what `kind` values?

**Repository evidence.**
- `package.json`: `packageManager: "bun@1.4.2"`, `engines.bun: ">=1.4.0"`, dependencies `ajv`,
  `nunjucks`, `yaml`, devDependencies `@types/node`, `@types/nunjucks`, `typescript`.
- `bun.lock` pins the exact versions; `jiti`/`commander`/`chokidar` are transitive entries, not
  declared manifest dependencies.
- Design §5.3: dependency `kind` is `runtime`/`toolchain`/`pipeline`/`decision`/`product`; `status`
  is `declared`/`resolved`/`pending`/`deferred`/`not_applicable`.
- S2 package §4.4: "S2.1 must choose manifest-name IDs"; no accepted source fixes a dependency list.

**Viable options.**
- **A (proposal default):** the 7 manifest names (`bun`, `ajv`, `nunjucks`, `yaml`, `typescript`,
  `@types/node`, `@types/nunjucks`) as IDs; `bun` = runtime/`declared`; `ajv`/`nunjucks`/`yaml` =
  runtime/`resolved`; `typescript`/`@types/*` = toolchain/`resolved`; `requires` edges from
  `COMP-CORE` (`bun`, `ajv`, `yaml`) and `COMP-RENDERER` (`nunjucks`).
- **B:** add pipeline/decision/product rows (for example `bun test`, `DEC-PR-56`, PAP) derived from
  prose rather than manifest names.
- **C:** encode no dependency rows.

**Recommended:** **A.** It follows the manifest-name rule exactly, is auditable against
`package.json`/`bun.lock`, and does not invent a parallel vocabulary. The unused toolchain rows are
honest; no check requires every dependency to be required by a component.

**Consequences.** A models only declared packages; B risks unsourced rows; C leaves the `requires`
relation and the dependency kind without project data.

**Blocks S2.1:** no with A.

## Q10 — Public-surface semantics — RESOLVED by owner decision (2026-11-04)

**Status:** resolved. Owner decision **Q10 = A**.

**Decision (owner-approved).**

1. All seven declared components are public responsibility units.
2. All twelve declared interface entities represent public surfaces.
3. `interface` is public by definition in this model; do not add a redundant `public` field.
4. Component `public` describes whether the component is a public responsibility unit, not whether its
   implementation is externally accessible.
5. `stability` is independent of public status; in particular `deferred` does not mean `private`.
6. Expected coverage: 7 components (1 covered, 6 uncovered); 12 interfaces (2 covered, 10 uncovered);
   19 public surfaces total (3 covered, **16 uncovered**).
7. Tests must assert the exact uncovered entity IDs, not only the aggregate count.
8. Do not suppress or reclassify warnings to obtain a preferred result; the 16 warnings represent
   uncovered public surfaces and remain visible for subsequent claim-coverage work.

**Repository evidence.** Design §5.2 (components are public responsibility units; interfaces are
public surfaces), §5.3 (`public` on components; no `public` on interfaces), §5.7
(`core000.surface.claim-missing`); current `structure.yml` and the five S1 claim subjects
(`COMP-CORE`, `IF-MANIFEST`, `IF-PROFILE-VALIDATOR`, `TB-PROFILE-EXEC`).

**Blocks S2.1:** no — resolved.
