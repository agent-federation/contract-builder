## Q1 — Phase and transition semantics — RESOLVED by owner decision (2026-11-03)

**Status:** resolved. The project owner confirmed the Q1 decisions on 2026-11-03 (PR #87
discussion). This record preserves the outcome; it is not an implementation authorization.

**Decision (owner-approved).**

1. **`requires` formalization.** The normative formalization is the post-run invariant: in a completed
   run, if a dependent phase is `passed` or `failed` (it was entered), every prerequisite is `passed`
   in that same run. This is labelled the maintainer-approved formalization of `requires`; it is
   **not** a consequence explicitly stated by contract §6.2.
2. **Eligibility terminology.** "All prerequisites `passed`" establishes eligibility only; it does not
   imply entry, execution or outcome. "Admitted", if used, means eligibility; admission is not an
   event.
3. **Skip semantics.** §6.2's failure-to-skip rule is read directly (owner-approved reading): a
   failing phase marks its **direct** dependents `skipped`. The contract text says "dependent
   phases"; "direct" is the adopted reading, and recursive propagation is not attributed to §6.2. For completed
   `BuildResult` records, the adopted completeness rule is that every declared phase has exactly one
   of the three existing states; a phase not entered because a prerequisite is non-passed is recorded
   as `skipped`. The completeness rule is a separate approved policy and supplies the
   downstream/transitive result without being misattributed to §6.2.
4. **Acyclicity.** An acyclic `hasPrerequisite` graph is required as an explicit well-formedness
   policy. It is not derived from the run-level invariant or from non-vacuity. It is enforced by the
   S2.1 test only; no policy code and no generic-core rule are added.
5. **Causal state production.** No causal state-production rule is added to the relation or claimed as
   part of the current semantics. `hasPrerequisite` encodes no execution-order, timing, scheduler,
   admission-event or state-production semantics.
6. **Incomplete observations.** Unknown/absent knowledge is scoped to incomplete or intermediate
   observations. There is no fourth `PhaseState` and no fourth completed-`BuildResult` state.
   Unknown is not silently mapped to `skipped`; any fail-closed mapping remains a separately labelled
   policy choice.

**Scope kept.** One `hasPrerequisite` relation (phase → phase, many, no inverse) carrying the eight
contract §6.2 edges; zero transition instances; the M1 declared sequence remains authoritative in the
execution plan; the artifact build-success gate remains result-level.

**Repository evidence.**
- `engine-public-contract.md` §6.1 declares 9 phases and `PhaseState = passed | failed | skipped`.
- §6.2 states the prerequisites and that "a failing phase marks dependent phases `skipped`".
- §8/§9 define `BuildResult.phases: Record<Phase, PhaseState>`.
- The diagnostic `phase` field is deferred (`C000-CT-008`), so runtime phase execution is not
  observable at this baseline.

**Classification.** Facts: the §6.2 prerequisite list, the failure→skip sentence, the three phase
states, the public `phases` shape. Owner-approved formalization: the post-run invariant.
Owner-approved reading/policies: the direct reading of the failure→skip sentence, the completeness
rule and acyclicity. Definitional: eligibility, empty-set vacuous eligibility. Not adopted: any causal
state-production rule, any execution-order/scheduler semantics, any fourth phase state.

**Deferred.** Runtime verification of eligibility/skip (needs phase observability), any future
transition/permitted-move graph and its source, and any change to the completeness/acyclicity
policies.

**Source synchronization.** Completed by PR #90 (merged `feb47ca`): the accepted design
(`core-000-self-contract.md` §5.4/§5.7/§8.7/§11) and the S2 package now record 29 relation
declarations, the Issue #84 description was updated, and the canonical decision record records the
Q1/Q3/Q5/Q10 decisions. No source action remains for this question; historical S1 snapshots are not
synchronization targets. S2.1 implementation was authorized on 2026-11-04 and is complete (slices
#100–#102; final PR #105 `dbc93de`, merged 2026-11-04).

**Blocks S2.1:** no — resolved.

**Status:** resolved. Owner decision **Q2 = B + D**.

**Decision (owner-approved).**

2. `enforcement: none`, `policy_status: settled`.

   positive draft build; it changes the review set and affects release gating (release is already

## Q5 — Reserved `kind` and domain-field access — RESOLVED by owner decision (2026-11-04)

**Status:** resolved. Owner decision **Q5 = A**, with bounded typed accessors.

**Decision (owner-approved).**

1. Preserve the generic IR reserved `Entity.kind` semantics.
2. Preserve the domain fields `dependency.kind` and `conformance_case.kind`; do not rename them and do
   not change generic IR extraction.
3. Provide profile-level typed accessors `dependencyKind(model, id)` and
   `conformanceCaseKind(model, id)`; a shared private helper is acceptable. Do not expose an
   unrestricted raw-document accessor to renderers or templates.
4. Accessors fail closed on: missing entity or source document; wrong entity kind; missing or
   duplicate source record; malformed record; missing or invalid domain `kind`.
5. Do not fall back to `Entity.kind` or silently substitute a default value.
6. Focused tests cover valid values, missing records, duplicate records, malformed records and
   invalid enum values.

**Repository evidence.** `spec/lib/ir.ts` reserves `kind`; design §5.3 names the domain fields; the
existing `evidenceKind` accessor is the bounded precedent; the earlier generalized `documentField`
idea is superseded by the typed pair.

**Blocks S2.1:** no — resolved.

2. All twelve declared interface entities represent public surfaces.
