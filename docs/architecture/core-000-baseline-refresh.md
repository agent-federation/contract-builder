### 1.2 Why the test counts differ

The accepted plan recorded `169 pass / 0 fail (12 files)`. That command was `bun test` before the
PAP verifier was added. At `da9a5f0`, `bun test` discovers both the engine tests and `pap/tests`,
so the same command now reports 292 tests across 21 files. The engine-only subset is still 169
tests across 12 files, and the PAP suite is 123 tests across 9 files; the two subsets sum to the
292 total. This is a counting change, not a new engine capability.

CI runs `bun test`, so CI now exercises both suites. Nothing in `spec/` or `profiles/` changed to
cause the difference.

## 3. Demonstrated impact of the PAP verifier (#64)

The PAP v0.1 verifier is a new, self-contained product boundary under `pap/`. The implementation
report records that it imports only `node:` built-ins and its own modules, never imports `spec/`,
`profiles/`, a renderer or a producer runtime, never renders Markdown, never executes package
content and never opens a network socket. The current tree confirms the import boundary. The
verifier is Tier B and Gate 3 remains open; it is not independent verification of PAP or of
CORE-000.

**Demonstrated impact on CORE-000: none found.**

- It does not export or consume a CORE-000 profile or project.
- It does not produce the Markdown artifact, `BuildResult`, diagnostics or `inputDigest` that the
  CORE-000 execution plan relies on.
- It does not verify CORE-000 claims; it verifies a PAP package with its own manifest, claims,
  policy, checks and report vocabulary.
- CORE-000's design §8.6 already treats PAP as a separate future external verifier path and does
  not claim that PAP consumes CORE-000 today. That remains true.
- PAP could later be part of an independent-verification path, but only as a separate product and
  only after its own review gates close. It does not change the CORE-000 decision record, the
  first-slice proposal or any evidence label in this refresh.

No CORE-000 assumption is inferred from the recency of #64. The no-impact finding is based on the
import boundary, the package format and the absence of a CORE-000 package, not on the merge date.

## 5. Deviations and limitations

1. **Local Bun version.** The commands above ran under Bun 1.4.4, while the repository pins and CI
   uses Bun 1.4.2. The CI run at `da9a5f0` passed `install`, `typecheck`, `test` and `check` under
   the pinned version, so the green result is not local-only. The local run is still a deviation
   and is recorded as such; the refreshed baseline does not claim that 1.4.4 and 1.4.2 are
   behaviourally identical for every check.
2. **No CORE-000 execution.** There is no CORE-000 project, profile, artifact, diagnostic set or
   `inputDigest` to run. The baseline commands prove the repository is green, not that the CORE-000
   hypothesis is true.
3. **No ephemeral run.** Nothing in this report ran in a fresh temporary environment, a container
   or a restricted process. No isolation is claimed.
4. **No independent verification.** A green suite, a merge, an approval event or this report is not
   independent verification. The independent-verification dimension remains `—` for every CORE-000
   claim.
5. **CI scope.** The cited CI run proves the repository's `check` workflow at `da9a5f0`; it does
   not prove the CORE-000 PoC, cross-platform determinism or future commits.
6. **Documentation drift.** This report records only the facts needed by the CORE-000 refresh. It
   does not re-audit the implementation-status matrix or the CORE-001 documentation drift; those
   remain as recorded in their own snapshots.
